# Vehicle Safety — user and setup manual

This application combines NHTSA recall and official investigation records in
PostgreSQL with consumer complaint documents in MongoDB. It also supports saved
vehicles, internal analyst cases and a small fleet recall/work-order workflow.

## 1. What you need

- Windows PowerShell, Python 3.13 or 3.14, PostgreSQL 18 and MongoDB Community.
  The new workflow was checked with PostgreSQL 18 and MongoDB 6.0 in isolated
  test databases. The earlier project snapshot used MongoDB 9.0.4.
- Access to running PostgreSQL and MongoDB servers, and a PostgreSQL setup account
  allowed to create the project database and restricted application roles.
- The four NHTSA ZIP archives in `data/raw/`. They are excluded from Git.

This is a local coursework application. Keep database services on localhost or
configure appropriate network security and MongoDB authentication yourself.
The application enforces ownership in its SQL queries; PostgreSQL row-level
security is not configured. Avoid exposing the development server to the Internet.

## 2. First setup on a new computer

Run each command separately from the repository root. Start both database
services using your normal local installation procedure.

```powershell
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Create `.env` only when it does not already exist. Edit it locally: set the
PostgreSQL setup account and password, host and port, and MongoDB URI. If MongoDB
requires authentication, put its authenticated URI in `.env`. Never commit or
share `.env`. The three restricted PostgreSQL role passwords and Flask signing
key are generated by the setup scripts below.

Download the approved public source archives. Existing files are kept, not
replaced. A local manifest records filenames, download time, byte counts and
SHA-256 hashes. Downloads and archive validation can take time.

```powershell
.\.venv\Scripts\python.exe scripts/download_sources.py
```

Construct the database objects and prepare the restricted application accounts:

```powershell
.\.venv\Scripts\python.exe scripts/setup_databases.py
.\.venv\Scripts\python.exe scripts/setup_readonly_user.py
.\.venv\Scripts\python.exe scripts/setup_auth.py
.\.venv\Scripts\python.exe scripts/setup_workflow.py
```

These commands create or update the project's schema, views, validators, indexes
and role grants. They do not drop the existing project database. On an existing
installation, run these commands after updating the code to apply migration 003,
the new views and grants. Retain the existing `.env` so existing role passwords
remain available. `setup_databases.py` requires a PostgreSQL setup account and
permission to update the MongoDB collections.

Import the four source files once. **This writes or refreshes reference records**
and records import runs; it is not a daily startup command. It can take several
minutes. Rerunning it intentionally refreshes source-owned fields, while keeping
application users, saved vehicles, cases and fleets.

```powershell
.\.venv\Scripts\python.exe scripts/import_all.py
```

Create the first administrator interactively. Choose a new application email
and password; this is separate from the database credentials in `.env`.

```powershell
.\.venv\Scripts\python.exe scripts/create_admin.py
```

The helper refuses to create a second first administrator. Normal registration
always creates a `NORMAL_USER`; an administrator can assign `ANALYST` or `ADMIN`
in the Administration screen.

## 3. Start and use the application

```powershell
.\.venv\Scripts\python.exe -m flask --app backend:create_app run --host 127.0.0.1 --port 5000
```

Open **http://127.0.0.1:5000/app**. Keep the terminal open while using the app.
Ctrl+C stops Flask; it does not stop the database services or erase their data.
`GET /` remains the original JSON API index.

1. In **Vehicle research**, enter a model year, make and model, then select a
   result. The overview separates official recalls, official investigations and
   consumer complaints. Explore the record tabs, filter complaints, and select a
   component to filter the complaint list.
2. Sign in to save a vehicle. **Saved vehicles** lets the owner open, rename or
   remove their own bookmarks.
3. An analyst or administrator can create an internal case from a selected
   vehicle or directly from a complaint. Link or unlink complaint ODI IDs for the
   same vehicle, manage tags and suspected components, add/edit/delete findings
   and notes, and change the case status. Status changes appear in its history.
4. In **Fleet recalls**, create a fleet, add the currently selected vehicle with a
   label, review model-level recall matches and create or update work orders.
   Removing a fleet vehicle also removes its work orders.
5. In **Administration**, an administrator can change roles, inspect import
   history/source availability, intentionally start a data refresh, and retry
   pending case synchronization. A refresh updates reference data and requires
   all four local archives. Its local log is `data/logs/web-import.log`.

Complaint counts represent reports, not confirmed defects or a safety rating.
A complaint can mention multiple components. Monthly bars show up to the last
12 months that contain reports; missing months are not displayed. Matches use
make/model/year, not an individual VIN. Follow the manufacturer's official VIN
lookup for a vehicle-specific recall determination.

## 4. Case synchronization and recovery

PostgreSQL stores case identity, ownership and status. MongoDB stores linked
complaints, notes, findings and tags. A PostgreSQL outbox records document
creation/deletion work in the same transaction as the case change. The app tries
the corresponding MongoDB operation immediately; retries are idempotent and
processed in order for each case.

If MongoDB is unavailable, case creation or deletion can return **202 / pending**.
The case page offers a retry for a pending creation; an administrator can retry
all pending work in Administration or run:

```powershell
.\.venv\Scripts\python.exe scripts/reconcile_cases.py
```

Pending deletion jobs survive removal of the SQL case. If a document is reported
missing without a pending job, investigate or restore it; the app does not silently
recreate it and discard its previous contents. This is an application-level
recovery mechanism, not a distributed database transaction.

## 5. Tests and benchmark

The regular suite runs with fake connections and made-up inputs:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

The additional live workflow test is skipped unless `VEHICLE_TEST_ENV_FILE`
points to a configuration for **local, separate PostgreSQL and MongoDB databases
whose names end in `_test`**. Prepare the schema and restricted roles in those
databases first. The test creates uniquely named synthetic records and removes
only its own fixtures; it never drops or empties a database.

```powershell
$env:VEHICLE_TEST_ENV_FILE = 'C:\path\to\isolated-test.env'
.\.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_workflows_live.py' -v
```

To check a synthetic case and fleet workflow linked to actual imported public
records, use the same dedicated test configuration after importing the source
data into those `_test` databases:

```powershell
.\.venv\Scripts\python.exe scripts/verify_real_workflow.py
```

For read-only counts, archive-hash checks and research API evidence on the
configured application databases, run `scripts/verify_readonly_workspace.py`.
Both commands write JSON evidence under ignored `verification/results/`.

The index benchmark copies a bounded sample to a PostgreSQL temporary table and a
randomly named MongoDB scratch collection in separate databases. It measures the
same query before and after its index within each DBMS, captures plans and checks
result counts. The PostgreSQL benchmark database must already exist; both target
names must end in `_benchmark` and differ from the source databases.

```powershell
$env:BENCH_POSTGRES_DB = 'vehicle_safety_benchmark'
$env:BENCH_MONGODB_DB = 'vehicle_safety_benchmark'
.\.venv\Scripts\python.exe scripts/benchmark_indexes.py --max-records 50000 --repeats 5
```

Results and raw plans are saved under ignored `benchmarks/results/`. The source
tables, collections and indexes are not altered. The sample is ordered rather
than random; describe its size, source snapshot, hardware, timings and limitations
in the report. SQL and MongoDB use different workloads, so their timings do not
establish that one DBMS is generally faster. A forcefully interrupted run can
leave its uniquely named scratch MongoDB collection in the benchmark database.

## 6. Submission and troubleshooting

- Create a new source/data/manual archive with the command below. It requires
  Git and all four source ZIPs, includes the current tracked and non-ignored
  source files plus available benchmark/verification JSON, and excludes `.env`,
  `.venv`, database storage and logs. Review the generated archive and manifest
  before submission. A new filename is created each time.

  ```powershell
  .\.venv\Scripts\python.exe scripts/package_submission.py
  ```

  The archive is written to ignored `submission/`; it is not submitted automatically.
- If `/api/health` reports a database unavailable, check its server, port and
  local `.env`; do not rerun the full import just to start the application.
- If a newly added endpoint reports a database permission error after a code
  update, apply the schema/views and rerun the reader/workflow setup commands.
- If a case is pending, restore MongoDB connectivity and retry synchronization.
- The final report, slides, five-member presentation video and actual submission
  still need the team's review and completion. Confirm current requirements and
  deadlines in XSite.
